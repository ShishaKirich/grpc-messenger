# Безопасность «Леса из Шишек»

Здесь описано, от чего защищены мессенджер и сайт, как именно и какие ограничения остаются. У каждой меры указан файл, где она реализована, а в `tests/` есть тест, который её проверяет. Подробности шифрования вынесены в [docs/CRYPTO.md](docs/CRYPTO.md).

## Что защищаем и от кого

**Активы:** переписка пользователей, учётные записи, ключи шифрования на устройствах.

**Нарушители:**

1. **Посторонний в сети** видит и может менять трафик между клиентом и сервером.
2. **Злоумышленник с клиентом**: у него есть свой аккаунт и он может слать серверу любые gRPC-запросы своим скриптом.
3. **Тот, кто украл базу данных** или резервную копию сервера.
4. **Сам сервер**, если его взломали или его владелец любопытен (honest-but-curious): хранит и пересылает сообщения, но читать их не должен.
5. **Тот, кто украл файл ключей** с компьютера пользователя.

## Модель угроз: мессенджер

| Угроза | Защита | Где в коде |
|---|---|---|
| Выдать себя за другого пользователя | Пользователь определяется только по токену сеанса из метаданных `authorization`. Поле `sender` и время ставит сервер, присланные клиентом значения игнорируются. Отправитель подписывает каждое сообщение обычного чата ключом Ed25519, поэтому даже сервер не может подделать сообщение. | `messenger_server/guard.py`, `messenger_service.py` (`SendMessage`), `e2e/regular.py` |
| Вход по одному украденному паролю | Вход в два шага. После пароля сервер выдаёт только одноразовый `challenge_id`, а токен сеанса появляется лишь после кода с почты, из приложения-аутентификатора или резервного кода. | `messenger_server/auth_service.py` |
| Подбор пароля и кода | Общий с сайтом журнал входов: 5 ошибок за 15 минут, и вход на этот email закрыт (пароли и коды TOTP считаются вместе). Каждый `challenge` даёт 5 попыток и сгорает. Код с почты: 6 цифр, 5 минут, 5 попыток, не больше 10 кодов в час. | `auth_service.py`, `auth_core/login_log.py`, `auth_core/otp.py` |
| Перебор аккаунтов | На неверный пароль и на несуществующий email ответ одинаковый, и пароль проверяется по хешу-заглушке, чтобы время ответа совпадало. | `auth_service.py` (`Login`), `auth_core/security.py` |
| Повторное использование кода или `challenge` | Атомарные `UPDATE ... WHERE used = 0`: из двух одновременных запросов проходит только один. Код TOTP принимается один раз (`totp_last_step`). | `auth_service.py` (`VerifyCode`), `auth_core/totp.py` |
| Кража токена сеанса из базы | В базе лежит только SHA-256 токена (256 бит случайности). | `auth_service.py`, `guard.py` |
| Угнанный сеанс | Сеансы общие с сайтом: «Завершить» и «Выйти везде» в личном кабинете отключают клиент, и открытый поток событий закрывается в течение 30 секунд. При каждом входе в мессенджер на почту приходит уведомление. | `guard.py`, `messenger_service.py` (`Subscribe`) |
| Перехват трафика | gRPC работает только по TLS. Клиент доверяет одному центру сертификации проекта, а не всем CA в системе. Режим без TLS включается только явным флагом `--insecure`. | `messenger_server/run_server.py`, `client/api.py`, `scripts/make_dev_cert.py` |
| Чтение переписки сервером или по украденной базе | Сквозное шифрование: ключи создаются на устройстве, сервер получает только шифротекст. | `e2e/`, `client/core.py` |
| Подмена ключей сервером (MITM) | Prekey подписан ключом устройства, подпись проверяют и сервер, и клиент. Код безопасности из 60 цифр можно сверить с собеседником. При смене ключа собеседника клиент показывает предупреждение, а отметка «проверено» снимается. | `e2e/keys.py` (`safety_number`), `client/core.py` (`bundle`) |
| Чтение чужой переписки через API (IDOR) | `History` отдаёт только сообщения, где вызывающий — отправитель или получатель. `Acknowledge` удаляет только адресованные себе сообщения. Ключи (`GetKeys`) доступны только друзьям. | `messenger_service.py` |
| Подделка дружбы | В старой версии клиент мог прислать текст `FRIEND_ACCEPTED:alice:bob` и «принять» заявку за другого. Теперь принять можно только входящую заявку, адресованную самому себе, отдельным вызовом `AnswerFriendRequest`. | `messenger_service.py` |
| Спам и навязчивые сообщения | Писать можно только друзьям, если никто из двоих не заблокировал другого. Если вас заблокировали, ваша заявка просто не доходит, и об этом не сообщается. Лимит: 60 сообщений в минуту. | `messenger_service.py` |
| Огромные сообщения (DoS) | Шифротекст не больше 64 КБ, заголовок не больше 4 КБ, gRPC отклоняет большие пакеты сам. Очередь событий на подключение ограничена. | `config.py`, `run_server.py`, `hub.py` |
| Утечка переписки через логи | Сервер не пишет в лог ни тексты, ни шифротекст. В старой версии каждое сообщение печаталось в консоль. | `messenger_server/` |
| Имена-двойники | Имя пользователя состоит только из латиницы, цифр и `_`, уникально без учёта регистра. Так нельзя завести `аlice` с кириллической «а». Неподтверждённые регистрации удаляются через сутки, чтобы никто не «занимал» чужие имена. | `web/main.py` (`USERNAME_RE`), `web/sessions.py` (`cleanup`) |
| Кража файла ключей с компьютера | Хранилище зашифровано ChaCha20-Poly1305 ключом из пароля через Argon2id (64 МБ, 3 прохода). Без пароля файл бесполезен. | `e2e/keystore.py` |
| XSS через сообщения | Сообщения показываются как обычный текст (`Qt.PlainText`), HTML не интерпретируется. | `client/ui/widgets.py` |

## Модель угроз: сайт (личный кабинет)

Сайт перешёл из проекта [2fa-auth-site](https://github.com/ShishaKirich/2fa-auth-site) почти без изменений. Общая логика вынесена в `auth_core/`, страницы остались в `web/`.

| Угроза | Защита | Где в коде |
|---|---|---|
| Утечка базы данных | Пароли хранятся как хеши Argon2id (19 МБ, 2 прохода). Коды хранятся как HMAC-SHA256 с секретным ключом. Токены сеансов и устройств хранятся как SHA-256. По содержимому базы нельзя войти ни в один аккаунт. | `auth_core/security.py`, `web/sessions.py` |
| Подбор пароля | После 5 неудачных попыток за 15 минут вход для этого email блокируется. Требования к паролю: длина от 10 символов, оценка zxcvbn не ниже 3, пароль не должен встречаться в утечках. | `web/main.py` (`login`), `auth_core/passwords.py` |
| Слабые и утёкшие пароли | zxcvbn учитывает словари, шаблоны клавиатуры, имя и email пользователя. Пароль проверяется по базе Have I Been Pwned методом k-анонимности: наружу уходят только первые 5 символов SHA-1, ответ дополняется фиктивными строками (`Add-Padding`). | `auth_core/passwords.py` |
| Перехват или подбор кода | Код состоит из 6 цифр, генерируется через `secrets` и живёт 5 минут. После 5 неверных попыток он сгорает, а при запросе нового кода старый перестаёт действовать. Попытка засчитывается до сравнения, сравнение выполняется за постоянное время. Лимит: не больше 10 кодов на пользователя в час, то есть не больше 50 попыток в час на миллион вариантов. | `auth_core/otp.py` |
| Взлом почтового ящика | Можно подключить приложение-аутентификатор (TOTP, RFC 6238). Тогда второй фактор не зависит от почты, и восстановление пароля по email тоже требует кода из приложения. | `auth_core/totp.py`, `web/main.py` (`reset`, `verify_totp_login`) |
| Утечка секрета TOTP из базы | Секрет хранится зашифрованным (Fernet: AES-128-CBC + HMAC-SHA256), ключ выводится из `SECRET_KEY`, которого в базе нет. QR-код строится на сервере (segno) и встраивается в страницу как `data:`-URI, поэтому секрет не уходит во внешние сервисы генерации QR. | `auth_core/totp.py` |
| Повтор перехваченного кода из приложения | Сохраняется номер последнего принятого 30-секундного интервала, и принимаются только более новые (атомарный `UPDATE ... WHERE totp_last_step < ?`). Допускается расхождение часов ±30 секунд. | `auth_core/totp.py` (`verify_and_consume`) |
| Перебор кода из приложения | Неверные коды считаются вместе с неверными паролями: после 5 ошибок за 15 минут вход блокируется. | `web/main.py` (`verify_totp_login`) |
| Потеря телефона | 10 одноразовых резервных кодов (около 40 бит каждый), в базе хранится HMAC. Использование кода сопровождается письмом с числом оставшихся кодов. Новые коды выдаются только по коду из приложения. | `auth_core/totp.py` |
| Отключение 2FA злоумышленником | Нужны и текущий пароль, и код из приложения (или резервный). Владельцу приходит письмо. | `web/main.py` (`totp_disable`) |
| Повторное использование кода (race condition) | Код помечается использованным атомарным `UPDATE ... WHERE used = 0`. Из двух одновременных запросов пройдёт только один. | `auth_core/otp.py` (`check_code`) |
| Перебор аккаунтов (user enumeration) | При неверном пароле и при несуществующем email выдаётся одно и то же сообщение. Для несуществующего email пароль проверяется по хешу-заглушке, чтобы время ответа было одинаковым. Регистрация на уже занятый email и восстановление пароля для несуществующего адреса выглядят так же, как обычно, а письма отправляются в фоне, чтобы не выдавать разницу во времени. Владельцу занятого адреса приходит уведомление о попытке регистрации. | `web/main.py` (`register`, `forgot`, `start_code_step`) |
| Почтовая бомбардировка (email bombing) | Повторная отправка кода не чаще раза в минуту, не больше 20 кодов с одного IP в час. | `auth_core/otp.py` (`issue_limit_reached`) |
| CSRF | Каждая форма содержит случайный токен, который сравнивается за постоянное время. Cookie сеанса выставляются с `SameSite=Lax`. | `auth_core/security.py`, все `POST` в `web/main.py` |
| XSS | Шаблоны Jinja2 экранируют данные автоматически. CSP `script-src 'self'` запрещает встроенные и чужие скрипты. Данные в письмах экранируются через `html.escape`. | `web/main.py` (`security_headers`), `auth_core/mailer.py` |
| Clickjacking | `frame-ancestors 'none'` и `X-Frame-Options: DENY`. | `web/main.py` |
| Кража cookie сеанса | Cookie выставляются с флагами `HttpOnly`, `SameSite=Lax` и `Secure` при HTTPS, плюс HSTS. Сеансы хранятся на сервере: при выходе запись удаляется, поэтому украденная копия cookie перестаёт работать. Сеанс живёт не больше 7 дней и завершается после суток бездействия. | `web/sessions.py` |
| Фиксация сеанса (session fixation) | После входа старое содержимое сессии стирается и выдаётся новый токен. | `web/sessions.py` (`create_session`) |
| Захваченный аккаунт | Уведомление на почту при входе с нового устройства. Список активных сеансов, кнопки «Завершить» и «Выйти на всех других устройствах». Смена или сброс пароля завершают все остальные сеансы и отзывают доверие ко всем устройствам. | `web/main.py` (`complete_login`, `password_changed`) |
| IDOR (чужие сеансы и устройства) | Все запросы на завершение сеанса или отзыв доверия содержат условие `AND user_id = ?` текущего пользователя. | `web/sessions.py` |
| Смена email злоумышленником | Нужен текущий пароль. Код приходит на новый адрес, а старому адресу отправляется уведомление. | `web/main.py` (`change_email`) |
| Смена пароля с чужого открытого сеанса | Нужен текущий пароль и код из письма. Новый пароль начинает действовать только после ввода кода. | `web/main.py` (`change_password`) |
| SQL-инъекции | Во всех запросах используются параметры `?`, строки в SQL не склеиваются. | все модули |
| Огромные запросы (DoS) | Ограничена длина всех полей. Пароль не длиннее 128 символов, так как Argon2 тратит ресурсы пропорционально длине. | `web/main.py`, `auth_core/config.py` |
| Кеширование личных страниц | `Cache-Control: no-store` на всех страницах, кроме статики. | `web/main.py` |
| Утечка секретов | Секреты хранятся только в `.env`, который не попадает в git. Приложение не запустится с почтой без собственного `SECRET_KEY`. Swagger и OpenAPI отключены. | `.gitignore`, `web/main.py` (`lifespan`) |

## Генератор паролей

Пароль генерируется в браузере и на сервер не уходит до отправки формы. Используется `crypto.getRandomValues`, а для равномерного распределения символов применяется rejection sampling (без смещения из-за деления по модулю). Пароль длиной 20 символов из набора в 70 символов даёт около 120 бит энтропии. В нём гарантированно есть символ каждого типа, после чего символы перемешиваются алгоритмом Фишера — Йетса. Из набора исключены похожие символы (`0/O`, `1/l/I`). Код находится в `web/static/app.js`.

## Известные ограничения

- **Метаданные видны серверу**: кто, кому и когда пишет, размер сообщений. Скрыть это можно только другой архитектурой (sealed sender, смешивание трафика).
- **Одно устройство на аккаунт для шифрования.** При входе с нового компьютера создаются новые ключи. Старые сообщения обычных чатов на новом устройстве не расшифруются, секретные чаты закрываются, а друзья видят предупреждение о смене ключа. Так же поступает Signal без переноса ключей.
- **В обычных чатах нет прямой секретности.** Если украсть ключ устройства и пароль от хранилища, можно расшифровать всю историю с сервера. Для важного есть секретные чаты.
- **Signed prekey не ротируется и нет одноразовых prekey (OPK).** Это ослабляет прямую секретность самого первого сообщения секретного чата. Ротация prekey в планах.
- **Пароль приходит на сервер при входе.** Хранилище ключей зашифровано тем же паролем, поэтому взломанный сервер теоретически может получить и пароль, и файл ключей. Но файл хранится на компьютере пользователя, а не на сервере. Полностью закрыть это можно протоколом OPAQUE.
- **Таймер самоуничтожения** зависит от честности клиента собеседника: модифицированный клиент может сохранить сообщение. Скриншоты экрана тоже не запрещены.
- **Лимит сообщений** хранится в памяти процесса и рассчитан на один сервер.
- **Email как второй фактор** (по умолчанию) слабее приложения-аутентификатора: если взломан почтовый ящик, взломан и второй фактор. Поэтому пользователю предлагается подключить приложение. Аппаратные ключи (WebAuthn / passkeys) пока не поддерживаются.
- **Смена `SECRET_KEY`** делает недействительными все подключённые приложения (секреты TOTP зашифрованы этим ключом) и все резервные коды. Ключ нужно хранить и не менять без необходимости.
- **Блокировка по email** позволяет злоумышленнику на 15 минут заблокировать вход чужому аккаунту, вводя неверные пароли. Это осознанный компромисс в пользу защиты от подбора.
- **Доверенное устройство**: если украдена cookie `device`, второй фактор на этом устройстве пропускается. Пароль при этом всё равно нужен. Доверие можно отозвать в кабинете, и оно отзывается автоматически при смене пароля.
- **Проверка по утечкам** выполняется через внешний сервис. Если HIBP недоступен, проверка пропускается (fail open), а в лог пишется предупреждение.
- **IP за прокси**: если сайт стоит за nginx или CDN, для правильного определения IP клиента нужно запускать uvicorn с `--proxy-headers --forwarded-allow-ips=<адрес прокси>`.
- **SQLite** подходит для одного сервера. Для нескольких серверов нужен PostgreSQL.

## Проверки в CI

- **Автотесты** (`pytest`): сайт, gRPC-сервер (вход, права доступа, подделка отправителя, IDOR, лимиты), криптография (подделка, повтор, порядок сообщений, прямая секретность) и логика клиента против настоящего сервера.
- **bandit**: статический анализ Python-кода.
- **pip-audit**: известные уязвимости в зависимостях.
- **CodeQL**: анализ кода от GitHub.
- **gitleaks**: поиск секретов во всей истории git.
