# Путеводитель по исходному коду

Проект состоит из пяти пакетов:

| Пакет | Что внутри |
|---|---|
| `auth_core/` | Общее ядро аккаунтов: настройки, база, пароли, коды, TOTP, письма, журнал входов. Им пользуются и сайт, и сервер мессенджера. |
| `web/` | Сайт — личный кабинет: регистрация, вход, настройки, сеансы. |
| `messenger_server/` | gRPC-сервер мессенджера. |
| `e2e/` | Сквозное шифрование. Работает только на клиенте, сервер этот пакет не импортирует. |
| `client/` | Клиент на PySide6. |

Сначала идёт часть про сайт и общее ядро, потом [про мессенджер](#мессенджер). Как устроено шифрование, описано отдельно в [CRYPTO.md](CRYPTO.md).

## Что хранится в cookie

- `session` подписана секретным ключом, подделать её нельзя. Внутри лежат:
  - `csrf` — токен для форм;
  - `pending` — действие, которое ждёт ввода кода (`user_id`, `email`, `purpose`, время начала);
  - `sid` — токен сеанса после входа. В базе (`sessions`) хранится только его SHA-256;
  - `reset` — разрешение задать новый пароль после ввода кода восстановления (на 10 минут).
- `device` — случайный токен устройства, живёт 400 дней. В таблице `devices` хранится его хеш.

## Назначения кодов (`purpose`)

| purpose | Когда выдаётся | Что происходит после ввода кода |
|---|---|---|
| `verify_email` | регистрация | почта подтверждена, вход |
| `login` | вход на сайт с недоверенного устройства | вход |
| `messenger_login` | вход в мессенджер (код с сайта здесь не подойдёт, и наоборот) | сервер выдаёт токен сеанса |
| `reset` | «Забыли пароль?» | страница `/reset` для нового пароля |
| `change_password` | настройки | применяется новый пароль из `payload` кода |
| `change_email` | настройки (код идёт на новый адрес) | применяется новый email из `payload` |
| `totp` | вход, если подключено приложение (письмо не отправляется) | `verify_totp_login()`: код из приложения или резервный код |

`payload` хранится в таблице `otp_codes`, поэтому новые данные начинают действовать только после ввода кода.

## Главные функции `main.py`

- `start_code_step()` (`web/main.py:156`): выдаёт код, отправляет письмо и ведёт на `/verify`. Если вызвать её с `user_id=None`, получится «пустышка»: страница выглядит как обычно, но код никуда не отправляется. Так сайт не выдаёт, зарегистрирован ли email.
- `complete_login()` (`web/main.py:186`): последний шаг любого входа. Запоминает устройство, создаёт сеанс, пишет журнал и отправляет письмо, если устройство новое.
- `password_changed()` (`web/main.py:207`): меняет пароль, завершает остальные сеансы и отзывает доверие ко всем устройствам.
- `verify()` (`web/main.py:438`): проверяет код и по `purpose` решает, что делать дальше.

## Сценарий входа

1. `login()`: лимит неудачных попыток, затем проверка пароля. Это первый фактор.
2. Если почта не подтверждена, пользователь получает код `verify_email`.
3. Если устройство доверенное (`sessions.is_trusted_device`), вход выполняется сразу.
4. Если подключено приложение, `start_totp_step()` сразу ведёт на `/verify`, где проверяется код из приложения (`verify_totp_login()`).
5. Иначе отправляется код `login` на почту, пользователь вводит его на `/verify`, и вызывается `complete_login()`. Это второй фактор.

## Приложение-аутентификатор: `auth_core/totp.py`

1. `/settings/totp/start`: после проверки пароля создаётся секрет (160 бит) и сохраняется зашифрованным, но защита ещё выключена.
2. `/settings/totp`: показывается QR-код со ссылкой `otpauth://` и ключ для ручного ввода.
3. `/settings/totp/confirm`: пользователь вводит код из приложения, это доказывает, что всё настроено. Защита включается, выдаются 10 резервных кодов.
4. При входе `verify_and_consume()` ищет, какому 30-секундному интервалу соответствует код, и принимает его, только если этот интервал новее последнего принятого. Так один код нельзя использовать дважды.

## Проверка кода: `check_code()` (`auth_core/otp.py:64`)

1. Берётся только последний код пользователя для этого действия.
2. Если он использован или истёк, возвращается `EXPIRED`.
3. Сначала засчитывается попытка (`attempts + 1`), и только потом код сравнивается.
4. При совпадении выполняется `UPDATE ... SET used = 1 WHERE used = 0`. Если два запроса пришли одновременно, пройдёт только один.

## Почему это работает при многих пользователях

- Все обработчики `async`, и `uvicorn --workers 4` запускает 4 процесса.
- Argon2 и zxcvbn нагружают процессор, поэтому они выполняются в отдельных потоках (`asyncio.to_thread`).
- Уведомления отправляются в фоне после ответа (`in_background`).
- SQLite работает в режиме WAL с автокоммитом (`auth_core/db.py:30`). Транзакции не держатся через `await`, поэтому блокировок нет.

## Как отлаживать

- Запуск с автоперезагрузкой: `uvicorn app.main:app --reload`. При `MAIL_BACKEND=console` коды печатаются в терминал строкой `[DEV] Код для ...`, уведомления — строкой `[DEV] Письмо для ...`.
- Посмотреть базу: `sqlite3 data/app.db`, затем, например, `SELECT id, user_id, ip, last_seen_at FROM sessions;`.
- Тесты: `pytest -q`. После любой правки стоит их прогнать.

## Вход в мессенджер

1. `Login()` (`messenger_server/auth_service.py:55`): общий лимит неудачных попыток, проверка пароля. Неверный email и неверный пароль дают одинаковую ошибку.
2. Сервер создаёт запись в `login_challenges` и возвращает клиенту случайный `challenge_id` (в базе только его хеш) и способ второго фактора. Если подключено приложение, письмо не отправляется.
3. `VerifyCode()` (`auth_service.py:94`): не больше 5 попыток на один `challenge_id`, он живёт 5 минут. Код с почты проверяется через `check_code()`, код приложения через `verify_and_consume()`.
4. После успеха создаётся обычный сеанс в `sessions` с пометкой `messenger:` в описании устройства. Поэтому сеанс мессенджера виден в кабинете сайта, и кнопка «Завершить» там отключает клиент.
5. На почту уходит уведомление о входе (в фоне).

## Как сервер проверяет права

- Каждый вызов, кроме входа, начинается с `authenticate()` (`guard.py:52`). Имя пользователя берётся только из сеанса, а не из запроса.
- `SendMessage()` (`messenger_service.py:212`): получатель должен быть другом и не заблокировать отправителя; лимит 60 сообщений в минуту; размер до 64 КБ. Отправитель и время ставятся сервером.
- Принять заявку можно, только если она действительно пришла (`AnswerFriendRequest`, строка 171). В старой версии клиент мог сам прислать «заявка принята».
- `Subscribe()` (строка 57) каждые 30 секунд проверяет, что сеанс ещё жив. Завершили сеанс на сайте — поток закрывается.

## Как клиент получает сообщения

- `EventStream` (`client/ui/worker.py`) держит поток `Subscribe` в отдельном потоке Qt и переподключается с растущей паузой.
- События передаются в `Messenger.handle_event()` (`client/core.py`), который расшифровывает сообщение и возвращает `Update` для интерфейса.
- Все остальные вызовы идут через `run_async()`, чтобы окно не зависало.
